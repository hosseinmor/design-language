# Components

Component documents are **design decision contracts**, not autogenerated copies of Figma, implementation props, or Storybook. Retrieve the **smallest relevant owning component** and only the related Foundation/Pattern/Accessibility source that resolves a real gap.

## Find the right component family

| Intent | Start here | Boundary to check |
|---|---|---|
| Trigger an action | [Button](button.md), [Icon Button](icon-button.md) | [Menu Button](menu-button.md) opens peer actions; [Combo Button](combo-button.md) offers a main action plus alternatives; [Toggle Button](toggle-button.md) selection remains draft/TBD |
| Choose a value or change a setting | [Checkbox](checkbox.md), [Radio](radio.md), [Select](select.md), [Autocomplete](autocomplete.md), [Chip](chip.md), [Choice Group](choice-group.md), [Switch / Toggle](switch.md) | Switch serves immediate binary settings; do not confuse selection with action activation |
| Enter text or numbers | [Text Input](text-input.md), [Number Input](number-input.md), [Textarea](textarea.md), [Password Input](password-input.md), [Search](search.md), [Rich Text Editor](rich-text-editor.md) | Number Input owns numeric value, persistent contextual unit, and optional steppers; specialized inputs reuse the shared Field contract |
| Navigate within hierarchy or to a destination | [Link](link.md), [Breadcrumb](breadcrumb.md), [Side Navigation](side-navigation.md) | Link is destination navigation, not an action Button; Breadcrumb conveys hierarchy; Side Navigation is a **draft** persistent-navigation contract, distinct from Menu and Drawer |
| Disclose content or switch views | [Accordion](accordion.md), [Tabs](tabs.md), [Content Switcher](content-switcher.md) | Accordion expands supporting content; Tabs and Content Switcher select peer views using distinct composition/interaction rules |
| Display anchored guidance | [Tooltip](tooltip.md), [Toggletip](toggletip.md), [Popover](popover.md), [Coachmark](coachmark.md) | [Contextual Guidance](../../foundations/interaction/contextual-guidance.md) owns cross-family intent and anchor rules |
| Show a task dialog or command menu | [Dialog](dialog.md), [Menu](menu.md) | [Modal](modal.md) is a legacy-name redirect to Dialog; [Dropdown Menu](dropdown-menu.md) is unverified terminology, not an approved Menu alias |
| Show feedback, loading or operation progress | [Notification](notification.md), [Progress Bar](progress-bar.md), [Progress Circle](progress-circle.md), [Skeleton](skeleton.md), [Progress Indicator](progress-indicator.md) | Progress Indicator expresses known workflow steps, not elapsed task progress; [Badge](badge.md) anatomy remains TBD; [Tag](tag.md) is a reviewed passive categorical label |
| Present chronological events | [Timeline](timeline.md) | Timeline shows event/schedule history, not a stepper; use [Progress Indicator](progress-indicator.md) for known workflow step states |
| Compare/manage structured records | [Data Table](table.md) | [Data Views pattern](../patterns/data-views.md) remains draft; [Table Runtime Contract](table-runtime-contract.md) is a component-annex proposal, not another public component or a verified Code API |
| Compose empty, paged or side-surface experiences | [Empty State](empty-state.md), [Pagination](pagination.md), [Drawer](drawer.md) | All three component docs are unverified scaffolds; [Empty States pattern](../patterns/empty-states.md) is **also a scaffold**, while [Data Views](../patterns/data-views.md) is draft. Follow the [Empty State content guidance](../../foundations/content/patterns/empty-states.md) for its evidence-backed messaging decisions; none of these links certifies a finished visual component. |

## Scope and documentation depth

A component document should answer, as concisely as its complexity allows:

1. What problem does the reusable component solve, and when should it be avoided?
2. Which meaningful design choices, states and behaviors are owned by this component?
3. Which composition, content and component-specific accessibility decisions matter?
4. Which decisions or implementation details remain open, and which linked live sources own them?

**Simple/native:** compact design contract, use native/accessibility references. **Stateful native-based:** clarify transitions, selection and validation. **Composite/custom:** explicit interaction, focus, keyboard and composition contracts. See the [component template](../../governance/document-templates/component-template.md) and [accessibility authoring contract](../../accessibility/component-accessibility-authoring-contract.md). Do not mechanically fill every section in long-form documents.

## Maturity is not shipment

| Evidence | What it means | What it does **not** mean |
|---|---|---|
| `knowledge_state: verified`, even in a `draft` file | Some owner-reviewed or validated design evidence is present | Every section is final, a Figma library is published, or code is shipped |
| `document_maturity: reviewed / final` | The stated **design-side scope** is complete enough for its intended use | Runtime API, interaction tests, a11y conformance or deployment has been verified |
| `design_status: ready-for-dev` / `ready-for-sandbox` | The intended design handoff or pilot can proceed | Production readiness or a registered Storybook/Code implementation |
| `document_maturity: scaffold` and `knowledge_state: unverified` | Topic, linked owner and unresolved design questions are reserved | An approved component, documented behavior, public variant or implementation |

The generated Manifest's document-level `status` is coarse and may report `draft` even where design decisions are reviewed; consult frontmatter and the **specific rule's evidence**, following [AI retrieval](../../ai/retrieval.md). Do not promote incomplete docs based on their length, visual polish or a recent `last_reviewed` date.

**Five reserved component scaffolds:** Badge, Drawer, Dropdown Menu, Empty State and Pagination. Tag has a reviewed design-side contract; its runtime source remains unverified. They retain open questions without inventing a production contract. Linked Patterns and Content documents may themselves be draft/scaffold; inspect each source's maturity separately.

## Keep out of component knowledge by default

- Generated prop/API tables and exact implementation syntax (owning [Code](../../integrations/code.md)).
- Every Figma variant and token-value dump (owning [Figma](../../integrations/figma.md) and [Tokens](../tokens/README.md)).
- Generic accessibility mechanics (owning [Accessibility](../../accessibility/router.md)); components state only resolved specific behavior.
- Generic action hierarchy, interaction or multi-component patterns (owning Foundations and Patterns).
- Completed migration history and exhaustive unexecuted test code.

Use the [Component Mapping Lookup Index](../../integrations/component-mapping-index.md) for targeted Figma→runtime identity evidence; do not load the large mapping registry by default. Existing long-form component documents can be simplified **when their owning component is next reviewed**, but do not silently delete verified design decisions, meaningful TBDs, or handoff evidence solely to shorten retrieval.
